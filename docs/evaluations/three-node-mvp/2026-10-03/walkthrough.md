## 已实际验证的职责与交接

- implementation-plan 曾调查现有结构与实现、形成有任务和检查的计划，并进入审批。S01 的恢复准备仍存在不足，因此不把“生成了计划”当成所有字段可靠。
- human-approval 曾展示审批选项、获得明确批准并记录范围。S03 的面板展示经过用户提醒和环境规则修订；不计为该轮首次自主完成。
- implementation 曾执行获批代码修改、单元检查、构建和实际模拟器交互；S06 有三账户视图及新 CSV 回读等依据。该结果是提醒和返工后完成。
- 原范围失败能继续调查、修复并交付新候选；S05 明确维持原授权并要求越界时重新审批。未把该特例推断为所有变更控制分支都已验证。
- 新的记录保留方式在本次两份文档 skill 的定向用例中实际验证：独立文件与追加编号章节、原格式复用与条件读取模板、报告完整但工作未达标。它们没有替 implementation 执行漏掉的应用检查。

## 初始失败、提醒与返工

按已有材料的时间顺序保留：

1. **20260929-121328 的更正**：S02 承认未运行独立 Web 构建，原构建输出为虚构；全量自动回读拿到旧 CSV，新文件同步拉取缺少独立日志，总体结论降级。后续成功或新日志不能把这轮改成通过。
2. **20260929-211529 的审批展示**：初次只交付等待审核摘要；用户要求在对话展示面板后，修订本地一句话输出限制并补面板。涉及现有 skill 展示契约与环境指令冲突；不能只归因于模板缺失。批准及后来单独请求 APK 打包是正常用户参与；原批准范围不含原生打包，不把该新增授权请求判作遗漏。
3. **20260930-110501 的环境限制和结论**：MuMu 当时未启动，端口拒绝连接；用户确认是自己未启动。无法执行该环境检查属于实际环境限制；同时报告“通过、满足所有标准”是结论与未验证项不一致，已有契约不允许这样报告。后来追加“用户报告真机验收通过”，只支持对应安装包及用户观察，不证明 Agent 做过 MuMu 检查。
4. **20261001-105439 的范围内补做与修复**：用户要求回读组合筛选新 CSV，并检查单账户拆分交易的汇总、分组、明细和导出一致性。属于提醒完成承诺的检查与修复；原范围内改正无需新增同范围审批。S06 的 100 元拆分为微信 40、支付宝 60，三视图及 CSV 核对完成，308 项测试的原始输出留存。这支持该候选修复后结果，保留首次交付遗漏。
5. **历史覆盖**：S06 17–20 行明确原 APK、旧 diff 和 status 已被覆盖且无真实副本。后续独立 closure 目录保留新证据是改进，不能恢复旧版本，也不能用新文件冒充旧文件。
6. **本次文档 skill 测试**：原首例额度中断单独保留，独立重试先过轨迹核验再启动后三例；其中一个链接检查命令错误由 Agent 在首次交付前自主修复。属于实际执行中的正常修正，没有用户补做提醒。

用户补充功能、明确批准与最终验收是正常参与。要求补展示已有审批契约、执行已承诺的检查、回读新产物或补交基本材料，应在对应节点和环境原因下保留。用户提醒后结果变好，不抹去先前交付质量。

## 问题归属与最小处理

| 问题 | 归属判断 | 处理与边界 |
|---|---|---|
| 承诺的自检未闭环、旧 CSV 被误当新结果、证据不支持通过 | 主要是执行方法及未遵循已有 implementation 自检／代码交付契约；个别原始轨迹不足 | 下一实战检查首次交付是否自主完成，保留真实候选和输出；不重复添加已有规则 |
| MuMu 未运行 | 环境限制；把缺项说成总体通过另属报告错误 | 明确所缺环境及未完成检查；用户报告可以独立记录，不能代替 Agent 检查 |
| 面板未在对话呈现 | 已有 human-approval 规则加本地输出限制冲突 | 旧环境已经更正；保留被提醒事实，不无证据认定要改审批 skill |
| status/diff 被当作完整检查点，保证“100% 恢复” | 未遵循已存在的恢复准备与前置条件契约 | 以后按需保存涉及内容并验证可恢复性；整理和收尾不替执行节点创建业务检查点 |
| 旧结论与关键证据被覆盖 | 历史保留失效；不同轮次精确版本不足，不能一概归因于当前规则未覆盖 | 当前三个节点已有保留规则；本轮只补齐 organize-docs、project-closeout 的自身契约并验证 |
| 两份文档 skill 缺少独立使用、阶段收尾、必填输出和格式分支契约 | 本轮确认的 skill 缺口 | 获批四文件最小修改已经完成；没有复制其他专业节点方法 |
| 未验证某个平台、独立分支或较新候选 | 未测试或证据不足 | 明确列出，按实际需要新增定向观察；不能统称“缺少专业 skill” |

最值得继续处理的是 G01：首次交付前 implementation 是否兑现批准计划中的必要检查，并把证据对应到实际候选。当前契约足够，本轮没有为同一失败重复加规则，也没有把完整路径验收、视觉验收、安全、CI、发布和结项都交给它。

## 未测试行为与历史限制

- 独立使用用户计划和授权、邻接 skill 缺失时的完整退路、专业 skill 优先复用及不可用时等效执行。
- 并行任务的界面／状态协调、子 Agent 冲突处理与安全暂停；实际按依赖选择串并行。
- 部分审批、需求及关键方案变化后的重新规划审批、仅继续已证明不受影响的任务；状态询问不误暂停。
- 向缺失或可用后续节点的自动交接、接收后续失败证据的完整契约，以及专业节点本身的验收方法。
- 三个 MVP 节点在不同软件项目、不同模型下的自主可靠性；本次四个文档用例不能补证明。
- 较新 S07 手势候选完整验证过程；其 APK 当前存在不等于本轮审核通过。
- 各历史运行的完整工具轨迹和准确 skill 版本、已丢失旧产物及旧变更快照；已有新文件不能补还原。
- 本阶段没有执行安全审计、CI 门禁、上架、开源发布、项目最终验收或发布后观测。

## 分别结论

**收尾记录完整性**：本轮记录已覆盖范围、条件、候选及位置、逐项对照、初始失败、提醒和返工、证据来源、未知及其影响、责任和实际交接。关键来源的本轮快照及新用例输入输出已经保存；历史缺失仍明确标记，完整记录不意味着全部历史证据齐备。

**范围内工作达标**：获批两份文档 skill 最小完善与四次定向验证达标，三节点阶段判断可以收尾并进入下一轮实战。MVP 的自主首次交付质量目标尚未建立，不能宣称完整工作流已稳定或产品已完成。业务最终可用和工作流可靠性分别判断，不因用户真机反馈或后续补救成功而合并成一个通过。
